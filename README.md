# АС «Скачки» — horse-racing-devops

Информационная система клуба любителей скачек: учёт лошадей, их владельцев, жокеев,
ипподромов, проводимых состязаний и результатов заездов.

Приложение разработано по **техническому заданию (ЛР 1)** и предназначено для
развёртывания на трёх стендах — **TEST**, **STAGE** и **PROD** — в рамках
**лабораторной работы № 2 «Виртуализация»**.

## Возможности

Предметная область по ТЗ: лошади (**кличка, пол, возраст, владелец**), владельцы
(**имя, адрес, телефон**), жокеи (**имя, адрес, возраст, рейтинг**), ипподромы,
состязания (**дата, время, место, название**), участники заездов и результаты
(**лошадь, жокей, занятое место, показанное время**).

Все семь функций, перечисленных в ТЗ, реализованы в графическом интерфейсе:

| № | Функция ТЗ | Где в приложении |
|---|-----------|------------------|
| 1 | Список участвующих жокеев и лошадей с местами и временем | Карточка состязания `/races/{id}` |
| 2 | Добавление нового состязания | `/races/new` |
| 3 | Добавление нового жокея | `/jockeys/new` |
| 4 | Добавление новой лошади (с владельцем) | `/horses/new` |
| 5 | Добавление результатов прошедшего состязания | `/races/{id}` → «Добавить участника заезда», строка результата |
| 6 | Список состязаний каждого жокея | Карточка жокея `/jockeys/{id}` |
| 7 | Список состязаний каждой лошади | Карточка лошади `/horses/{id}` |

Дополнительно: разграничение прав по ролям, управление учётными записями,
поиск и фильтры по всем справочникам, постраничный вывод, сводка на главной
странице, JSON-API и проверка работоспособности стенда.

Отдельно выполнено требование ТЗ к **базовой подсистеме** — навигация между
разделами «Состязания», «Жокеи», «Лошади», «Владельцы» и «Результаты».
Раздел «Результаты» (`/results`) собирает итоги всех заездов в одну таблицу
с фильтрами по ипподрому и поиском по состязанию, лошади, жокею или ипподрому.

## Стек

| Слой | Технология | Почему |
|------|-----------|--------|
| Язык | Python 3.11+ | Скриптовый ЯП: по ЛР 2 достаточно «запустить прототип», сборка не требуется |
| Веб-фреймворк | FastAPI + Uvicorn | Требование ТЗ к GUI выполняется браузером; автоматическая документация API |
| ORM | SQLAlchemy 2.0 | Реляционная СУБД, целостность данных средствами СУБД |
| СУБД | SQLite (по умолчанию) / PostgreSQL | Один и тот же код, переключение через `DATABASE_URL` |
| Шаблоны | Jinja2 | Серверный рендеринг, интерфейс на русском языке |
| Тесты | pytest + httpx (TestClient) | Автоматизированные тесты (роль тестировщика по ТЗ) |

Внешние CDN не используются: интерфейс работает на стендах без доступа в интернет.

## Быстрый старт

```bash
git clone https://github.com/MrTimofeys/horse-racing-devops.git
cd horse-racing-devops

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # при необходимости поправьте стенд
python -m app.cli run              # http://127.0.0.1:8080
```

При первом запуске создаются таблицы, демонстрационные учётные записи и
демонстрационный набор данных. Откройте <http://127.0.0.1:8080> и войдите.

Проверка готовности стенда (используется в ЛР 2):

```bash
curl -s http://127.0.0.1:8080/api/health
```

```json
{"status":"ok","stand":"TEST","database":{"dialect":"SQLite","available":true,"schema_ready":true}}
```

Если СУБД недоступна, стенд всё равно поднимается и честно об этом сообщает:

```json
{"status":"degraded","stand":"STAGE","database":{"dialect":"PostgreSQL","available":false,"schema_ready":false,"error":"..."}}
```

Страницы при этом отдают `503` с перечнем того, что нужно проверить, а схема
создастся сама, как только СУБД станет доступна — перезапуск службы не нужен.

## Демонстрационные учётные записи

| Логин | Пароль | Роль | Права |
|-------|--------|------|-------|
| `admin` | `admin123` | Администратор | Просмотр, изменение, удаление, управление пользователями |
| `operator` | `operator123` | Оператор | Просмотр, добавление и изменение данных |
| `viewer` | `viewer123` | Наблюдатель | Только просмотр |

> **Важно.** Это учётные записи для стендов TEST и STAGE. На стенде PROD пароли
> обязательно меняются (`python -m app.cli set-password`), а подсказка на странице
> входа отключается переменной `DEMO_LOGIN_HINT=false`.

## Соответствие требованиям ТЗ

| Требование ТЗ | Реализация |
|---------------|-----------|
| Визуальный графический интерфейс (GUI) | Веб-интерфейс: `app/templates/`, стили `app/static/css/style.css` |
| Единый дизайн, одинаковое расположение элементов | Общий макет `base.html`, единые компоненты форм, таблиц и кнопок |
| Русский язык интерфейса | Все шаблоны, сообщения об ошибках и валидация — на русском |
| Хранение в связанных таблицах реляционной БД | 8 таблиц, внешние ключи, каскады, ограничения целостности |
| Целостность данных средствами СУБД | `UNIQUE`, `CHECK`, `FOREIGN KEY`, `ON DELETE CASCADE/RESTRICT/SET NULL` |
| Авторизация пользователей | Вход по логину и паролю, сессии в БД, cookie `HttpOnly` + `SameSite=Lax` |
| «Слепые» пароли (символы не показываются) | `<input type="password">`; пароли хранятся как PBKDF2-HMAC-SHA256 |
| Разграничение доступа на уровне задач | Роли `admin` / `operator` / `viewer`, зависимости `require_user` / `require_editor` / `require_admin` |
| Исключение единовременной полной выгрузки данных | Постраничный вывод (`app/pagination.py`), серверные фильтры и поиск |
| Кроссплатформенность (Windows 10+, macOS, CentOS) | Чистый Python, путь к БД и порт задаются через окружение |
| Одновременная работа 10 пользователей | Uvicorn с пулом потоков, индексы по полям поиска и внешним ключам |
| Логирование и протоколирование | Журнал приложения, `journalctl` / файл лога на стенде |
| Резервное копирование данных | `scripts/backup.sh` для SQLite и PostgreSQL: создание копии, список копий, восстановление |
| Автоматическое резервное копирование | Таймер `skachki-backup.timer`, ежедневно в 03:30; ставится вместе со стендом |

## Конфигурация стенда

Все параметры читаются из переменных окружения (файл `.env`), поэтому один и тот
же код разворачивается на всех стендах без изменений.

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `STAND_NAME` | `local` | Имя стенда: `test` / `stage` / `prod` — выводится в шапке интерфейса |
| `DATABASE_URL` | `sqlite:///instance/skachki.db` | Строка подключения к СУБД |
| `APP_HOST` | `0.0.0.0` | Адрес прослушивания |
| `APP_PORT` | `8080` | Порт приложения |
| `SESSION_TTL_HOURS` | `12` | Время жизни сессии авторизации |
| `AUTO_SEED` | `true` | Создавать учётные записи при старте, если их нет |
| `SEED_DEMO_DATA` | `true` | Наполнять пустую базу демонстрационными данными |
| `DEMO_LOGIN_HINT` | `true` | Показывать подсказку с демо-учётками на странице входа |

Пример для стенда STAGE:

```dotenv
STAND_NAME=stage
DATABASE_URL=postgresql+psycopg://skachki:skachki@127.0.0.1:5432/skachki
APP_PORT=8080
SEED_DEMO_DATA=false
DEMO_LOGIN_HINT=false
```

## Работа с базой данных

```bash
python -m app.cli info              # параметры текущего стенда
python -m app.cli init-db           # создать таблицы
python -m app.cli seed --demo       # учётные записи + демонстрационные данные
python -m app.cli stats             # количество записей в таблицах
python -m app.cli check             # проверить подключение к СУБД
python -m app.cli list-users        # список пользователей
python -m app.cli create-user --username ivan --password secret1 --role operator
python -m app.cli set-password --username ivan --password newsecret
python -m app.cli reset --yes --demo   # полностью пересоздать схему
```

### Переключение на PostgreSQL

```bash
pip install -r requirements-postgres.txt
export DATABASE_URL="postgresql+psycopg://skachki:skachki@127.0.0.1:5432/skachki"
python -m app.cli check
python -m app.cli seed --demo
```

Схема создаётся автоматически при старте приложения.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest                              # 152 теста
pytest --cov=app --cov-report=term-missing
```

Тесты используют отдельную базу `instance/test_skachki.db` и не затрагивают
рабочие данные. Покрыто: авторизация и права ролей, все семь функций ТЗ,
валидация форм, ограничения целостности, разбор показанного времени, JSON-API,
а также поведение стенда при недоступной СУБД (`tests/test_availability.py`).

Тот же набор можно прогнать и на PostgreSQL — убедиться, что стенды STAGE и PROD
ведут себя так же, как TEST на SQLite. Достаточно задать `DATABASE_URL`:

```bash
export DATABASE_URL="postgresql+psycopg://skachki:пароль@127.0.0.1:5432/skachki_test"
pytest                              # те же 152 теста
```

Схема в указанной базе пересоздаётся автоматически, поэтому она должна быть
отдельной и не содержать нужных вам данных.

## Непрерывная интеграция

При каждом изменении в `main` и в запросах на слияние GitHub Actions выполняет
`.github/workflows/ci.yml`:

| Задание | Что проверяется |
|---------|-----------------|
| `tests-sqlite` | Полный набор тестов на SQLite под Python 3.11 и 3.12 |
| `tests-postgresql` | Тот же набор на PostgreSQL 16 (служба поднимается в контейнере) |
| `deploy-scripts` | Скрипты развёртывания всех трёх стендов и их синтаксис |

Это защищает от расхождения стендов: если изменение сломает поведение на
PostgreSQL, оно не попадёт в `main` незамеченным.

Дополнительно `.github/workflows/deploy.yml` выполняет **настоящее развёртывание**
на Ubuntu 24.04 LTS — том же выпуске, что и на стендах ЛР 2. Тем же скриптом,
который применяется на виртуальных машинах, устанавливаются средства разработки,
создаются системный пользователь и служба systemd, после чего проверяется, что
стенд отвечает на `/api/health` и пускает администратора. Стенды TEST и STAGE
разворачиваются параллельно, поэтому путь развёртывания проверяется на обеих
СУБД до того, как его выполнят на виртуальных машинах.

## JSON-API

| Метод | Адрес | Назначение |
|-------|-------|-----------|
| GET | `/api/health` | Проверка работоспособности стенда (без авторизации) |

| GET | `/api/stats` | Сводная статистика |

## Развёртывание на стендах TEST / STAGE / PROD

Полная пошаговая инструкция для лабораторной работы № 2 — в
**[docs/DEPLOY_LR2.md](docs/DEPLOY_LR2.md)**: создание виртуальных машин,
объединение их в локальную сеть, клонирование репозитория, установка средств
разработки и запуск приложения на каждом стенде.

Кратко, на каждой виртуальной машине:

```bash
git clone https://github.com/MrTimofeys/horse-racing-devops.git
cd horse-racing-devops
sudo bash scripts/provision-ubuntu.sh      # Python, git, средства сборки
sudo bash scripts/install-stand.sh test    # или stage / prod
curl -s http://127.0.0.1:8080/api/health
```

Скрипты развёртывания можно проверить и **без виртуальной машины** — они
исполняются в песочнице с заглушками системных утилит:

```bash
bash scripts/check-deploy.sh test                  # 25 проверок
bash scripts/check-deploy.sh stage --with-postgres # 18 проверок
bash scripts/check-deploy.sh prod --with-postgres  # 19 проверок
```

## Модель данных

```
owners ──< horses ──┐
                    ├──< race_results >──┬── races >── hippodromes
jockeys ────────────┘                    └── (место, показанное время)
users ──< user_sessions
```

Подробное описание таблиц, связей и ограничений — в
**[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)**.

Таблица `race_results` описывает и заявленный состав заезда (`place` и
`finish_time_seconds` пусты), и его результат — после того как место и время внесены.

## Безопасность

- Пароли хранятся только в виде хеша PBKDF2-HMAC-SHA256 (260 000 итераций, случайная соль).
- В базе хранится хеш токена сессии; утечка БД не даёт войти под пользователем.
- Cookie сессии: `HttpOnly` и `SameSite=Lax`.
- Сообщение об ошибке входа не раскрывает, существует ли такой логин.
- Все изменяющие запросы проходят через серверные проверки прав и валидацию;
  ввод пользователя экранируется шаблонизатором Jinja2.
- Запись удаляется только при отсутствии связанных данных (владелец с лошадьми,
  ипподром с состязаниями, лошадь или жокей с историей заездов).
