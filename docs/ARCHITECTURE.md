# Архитектура АС «Скачки»

## Назначение

Приложение реализует предметную область по ТЗ ЛР 1: учёт лошадей, их владельцев,
жокеев, ипподромов, состязаний и результатов заездов. Пользователь работает через
веб-интерфейс; серверная часть отдаёт HTML-страницы и JSON-API.

### Таблицы

| Таблица | Назначение | Ключевые ограничения |
|---------|-----------|----------------------|
| `users` | Учётные записи | `username` уникален; `role IN ('admin','operator','viewer')` |
| `user_sessions` | Сессии авторизации | `token_hash` уникален; `ON DELETE CASCADE` от `users` |
| `owners` | Владельцы лошадей | — |
| `horses` | Лошади | `age` в диапазоне 1–39; `sex` из перечня; `owner_id` → `ON DELETE SET NULL` |
| `jockeys` | Жокеи | `age` 16–99; `rating` 0–1000 |
| `hippodromes` | Ипподромы | `ON DELETE RESTRICT` со стороны `races` |
| `races` | Состязания | `status IN ('planned','finished','cancelled')`; индекс по дате |
| `race_results` | Состав заезда и результаты | см. ниже |

### Ограничения таблицы `race_results`

| Ограничение | Зачем |
|-------------|-------|
| `UNIQUE (race_id, horse_id)` | Лошадь заявлена в заезде один раз |
| `UNIQUE (race_id, jockey_id)` | Жокей заявлен в заезде один раз |
| `UNIQUE (race_id, place)` | Занятое место в заезде не повторяется (NULL допускает много записей) |
| `CHECK (place IS NULL OR place > 0)` | Место — положительное число |
| `CHECK (finish_time_seconds IS NULL OR finish_time_seconds > 0)` | Время положительно |
| `ON DELETE CASCADE` от `races` | Удаление состязания убирает состав заезда |
| `ON DELETE CASCADE` от `horses`, `jockeys` | Каскад на уровне СУБД; приложение отдельно запрещает удаление участников истории |

**Ключевое проектное решение.** Одна строка `race_results` описывает и заявку на
участие, и результат. Пока `place` и `finish_time_seconds` пусты — это объявленный
состав предстоящего заезда; после внесения значений запись становится результатом.
Это позволяет одной таблицей покрыть и функцию 1 ТЗ (состав заезда), и функцию 5
(внесение результатов), не дублируя данные.

### Хранение показанного времени

В ТЗ время указано как «показанное в заезде время» без формата. Принято решение
хранить его числом секунд (`FLOAT`) — так значения можно сравнивать и сортировать
в SQL. Пользователь вводит время в привычном виде `минуты:секунды,сотые`
(`2:05,30`), разбор и вывод выполняют `app.utils.parse_race_time` и
`app.utils.format_race_time`.

## Авторизация и права

1. `POST /login` проверяет пароль через PBKDF2-HMAC-SHA256 и создаёт запись в
   `user_sessions`; в cookie уходит случайный токен, в БД — только его SHA-256.
2. При каждом запросе `app/deps.resolve_session` находит сессию, проверяет срок
   действия и активность пользователя; просроченные сессии удаляются.
3. Права проверяются зависимостями FastAPI:

| Зависимость | Кто допускается |
|-------------|-----------------|
| `require_user` | Любой авторизованный (просмотр) |
| `require_editor` | `admin`, `operator` (создание и изменение) |
| `require_admin` | `admin` (удаление, управление пользователями) |

4. Неавторизованный запрос к странице получает `303 → /login`, к `/api/*` — `401`
   в формате JSON. Недостаток прав даёт `403` со страницей, объясняющей причину.

## Обработка ошибок

| Ситуация | Поведение |
|----------|-----------|
| Ошибка ввода в форме | Повторный вывод формы со `400` и понятным сообщением на русском |
| Объект не найден | `404` со страницей «Страница не найдена» |
| Недостаточно прав | `403` со страницей, где указана роль пользователя |
| **СУБД недоступна** | `503` со страницей, где перечислено, что проверить; запросы к `/api/*` получают JSON |
| Неожиданная ошибка | `500`, подробности в журнале приложения |

## Отказоустойчивость при недоступной СУБД

На стендах STAGE и PROD приложение работает с PostgreSQL, который при загрузке
системы может подниматься позже службы приложения. Поэтому:

1. **Приложение стартует даже без базы.** Недоступность СУБД не прерывает запуск
   службы — в журнал выводится понятное сообщение с указанием строки подключения.
   Без этого служба systemd ушла бы в бесконечный перезапуск со стеком вызовов.
2. **Состояние видно извне.** `GET /api/health` всегда отвечает `200` и сообщает
   `status: degraded`, а также поля `database.available`, `database.schema_ready`
   и `database.error`. Это позволяет отличить «служба не поднялась» от
   «служба работает, а база — нет».
3. **Схема создаётся автоматически при восстановлении.** Факт успешного создания
   схемы запоминается в процессе (`app/database.py`, флаг `_schema_ready`). Если
   СУБД была недоступна при старте, `GET /api/health` повторит создание схемы и
   загрузку начальных данных — перезапуск службы не требуется.
4. **Обработчики ошибок не обращаются к базе.** Страница `503` отрисовывается
   функцией `render_offline` (в отличие от остальных страниц ошибок), иначе
   обработчик упал бы повторно. Обработчик `500` пробует обычный путь и
   откатывается на `render_offline`, если база недоступна.

Проверено тестами `tests/test_availability.py` (8 тестов): старт без СУБД,
`degraded` в `/api/health`, страница `503`, JSON `503` для `/api/*`,
доступность страницы входа и автоматическое создание схемы после
восстановления СУБД.

## Постраничный вывод

ТЗ запрещает единовременную полную выгрузку данных. Все списки отдаются
страницами (`app/pagination.py`, по 20 записей, максимум 100), а фильтрация и
поиск выполняются на стороне СУБД.

## Проверка на двух СУБД

Приложение разрабатывалось с расчётом на то, что стенд TEST работает на SQLite,
а STAGE и PROD — на PostgreSQL. Чтобы поведение стендов не расходилось, это
проверяется автоматически.

**Одинаковый результат на обеих СУБД.** Полный набор тестов проходит и на SQLite,
и на PostgreSQL — 152 теста в обоих случаях. Для запуска на PostgreSQL достаточно
задать `DATABASE_URL` (см. `tests/conftest.py`, константа `EXTERNAL_DATABASE_URL`).

**Что специально сделано переносимым:**

| Место | Решение |
|-------|---------|
| Поиск по тексту | Везде используется `ilike()`. В PostgreSQL он зависит от языка и работает правильно. Встроенные `lower`/`upper` в SQLite обрабатывают **только латиницу**, поэтому для SQLite они переопределяются функциями Python (см. `app/database.py`): без этого поиск по русскому тексту в другом регистре ничего не находил |
| Схема | Никаких SQLite-специфичных типов: `create_all` компилируется и в `SERIAL`, и в `AUTOINCREMENT` |
| Уникальность места в заезде | `UNIQUE (race_id, place)`: и в SQLite, и в PostgreSQL значения `NULL` считаются различными, поэтому заявленный состав без мест не конфликтует |
| Внешние ключи | В SQLite включается `PRAGMA foreign_keys=ON` (по умолчанию выключен); в PostgreSQL проверяются всегда |
| Время заезда | Хранится числом секунд (`FLOAT`), поэтому сортировка и сравнение одинаковы |
| Резервное копирование | `scripts/backup.sh` определяет СУБД по строке подключения: `sqlite3 .backup` или `pg_dump` |

**Проверено на настоящем PostgreSQL 16:** создание схемы, загрузка
демонстрационных данных (8 лошадей, 6 жокеев, 4 состязания, 12 участников заездов),
работа веб-интерфейса и JSON-API, восстановление резервной копии с полным
совпадением количества записей и сохранением всех ограничений целостности,
а также восстановление стенда после остановки и повторного запуска СУБД.
