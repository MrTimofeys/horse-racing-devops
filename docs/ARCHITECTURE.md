# Архитектура АС «Скачки»

## Назначение

Приложение реализует предметную область по ТЗ ЛР 1: учёт лошадей, их владельцев,
жокеев, ипподромов, состязаний и результатов заездов. Пользователь работает через
веб-интерфейс; серверная часть отдаёт HTML-страницы и JSON-API.

### Таблицы

| Таблица | Назначение | Ключевые ограничения |
|---------|-----------|----------------------|
| `users` | Учётные записи | `username` уникален; `role IN ('admin','operator','viewer')` |
| `user_sessions` | Сессии авторизации | `token_hash` уникален; `ON DELETE CASCADE` от `users` |
| `owners` | Владельцы лошадей | — |
| `horses` | Лошади | `age` в диапазоне 1–39; `sex` из перечня; `owner_id` → `ON DELETE SET NULL` |
| `jockeys` | Жокеи | `age` 16–99; `rating` 0–1000 |
| `hippodromes` | Ипподромы | `ON DELETE RESTRICT` со стороны `races` |
| `races` | Состязания | `status IN ('planned','finished','cancelled')`; индекс по дате |
| `race_results` | Состав заезда и результаты | см. ниже |

### Ограничения таблицы `race_results`

| Ограничение | Зачем |
|-------------|-------|
| `UNIQUE (race_id, horse_id)` | Лошадь заявлена в заезде один раз |
| `UNIQUE (race_id, jockey_id)` | Жокей заявлен в заезде один раз |
| `UNIQUE (race_id, place)` | Занятое место в заезде не повторяется (NULL допускает много записей) |
| `CHECK (place IS NULL OR place > 0)` | Место — положительное число |
| `CHECK (finish_time_seconds IS NULL OR finish_time_seconds > 0)` | Время положительно |
| `ON DELETE CASCADE` от `races` | Удаление состязания убирает состав заезда |
| `ON DELETE CASCADE` от `horses`, `jockeys` | Каскад на уровне СУБД; приложение отдельно запрещает удаление участников истории |

**Ключевое проектное решение.** Одна строка `race_results` описывает и заявку на
участие, и результат. Пока `place` и `finish_time_seconds` пусты — это объявленный
состав предстоящего заезда; после внесения значений запись становится результатом.
Это позволяет одной таблицей покрыть и функцию 1 ТЗ (состав заезда), и функцию 5
(внесение результатов), не дублируя данные.

### Хранение показанного времени

В ТЗ время указано как «показанное в заезде время» без формата. Принято решение
хранить его числом секунд (`FLOAT`) — так значения можно сравнивать и сортировать
в SQL. Пользователь вводит время в привычном виде `минуты:секунды,сотые`
(`2:05,30`), разбор и вывод выполняют `app.utils.parse_race_time` и
`app.utils.format_race_time`.

## Авторизация и права

1. `POST /login` проверяет пароль через PBKDF2-HMAC-SHA256 и создаёт запись в
   `user_sessions`; в cookie уходит случайный токен, в БД — только его SHA-256.
2. При каждом запросе `app/deps.resolve_session` находит сессию, проверяет срок
   действия и активность пользователя; просроченные сессии удаляются.
3. Права проверяются зависимостями FastAPI:

| Зависимость | Кто допускается |
|-------------|-----------------|
| `require_user` | Любой авторизованный (просмотр) |
| `require_editor` | `admin`, `operator` (создание и изменение) |
| `require_admin` | `admin` (удаление, управление пользователями) |

4. Неавторизованный запрос к странице получает `303 → /login`, к `/api/*` — `401`
   в формате JSON. Недостаток прав даёт `403` со страницей, объясняющей причину.

## Обработка ошибок

| Ситуация | Поведение |
|----------|-----------|
| Ошибка ввода в форме | Повторный вывод формы со `400` и понятным сообщением на русском |
| Объект не найден | `404` со страницей «Страница не найдена» |
| Недостаточно прав | `403` со страницей, где указана роль пользователя |
| Неожиданная ошибка | `500`, подробности в журнале приложения |

## Постраничный вывод

ТЗ запрещает единовременную полную выгрузку данных. Все списки отдаются
страницами (`app/pagination.py`, по 20 записей, максимум 100), а фильтрация и
поиск выполняются на стороне СУБД.
