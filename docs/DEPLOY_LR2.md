## Шаг 2. Создание трёх виртуальных машин

Для каждой из трёх ВМ одинаковые действия:

1. Parallels Desktop → **File → New…** → *Install Windows or another OS from a

   * 2 CPU, **2 ГБ RAM**, 20 ГБ диска.

После первой установки удобно сделать клон:

```text
Parallels → правый клик по ВМ → Clone… → Clone with a new name
```

## Шаг 3. Единая локальная сеть

### 3.1. Тип сети в Parallels

Для каждой ВМ: **Configure → Hardware → Network → Shared Network**.

`Shared Network` в Parallels создаёт изолированную сеть `10.211.55.0/24`, в которой
все виртуальные машины видят друг друга напрямую. Это ровно то, что требуется в
задании 3, и при этом ВМ не «торчат» в домашнюю/университетскую сеть.

> Отличие от других режимов — см. [вопрос 1 для защиты](#вопрос-1-типы-сетей-для-виртуальных-машин):
> `Bridged` подключает ВМ к физической сети как отдельное устройство,
> `Host-Only` изолирует ВМ от внешней сети, `NAT` даёт выход наружу, но запрещает
> входящие подключения.

### 3.2. Статические адреса (рекомендуется для отчёта)

По умолчанию Parallels раздаёт адреса по DHCP, и они могут меняться. Для
предсказуемости зададим статические адреса через `netplan`.

Узнайте имя интерфейса:

```bash
ip -brief link
```

Обычно это `enp0s5`. Создайте файл конфигурации (подставьте своё имя интерфейса):

```bash
sudo tee /etc/netplan/99-stand.yaml >/dev/null <<'YAML'
network:
  version: 2
  ethernets:
    enp0s5:
      dhcp4: false
      addresses: [10.211.55.11/24]     # .12 для STAGE, .13 для PROD
      routes:
        - to: default
          via: 10.211.55.1
      nameservers:
        addresses: [10.211.55.1, 8.8.8.8]
YAML

sudo chmod 600 /etc/netplan/99-stand.yaml
sudo netplan apply
```

Проверьте адрес:

```bash
ip -brief address show enp0s5
```

## Диагностика

| Симптом | Причина и решение |
|---------|-------------------|
| ВМ не пингуют друг друга | В настройках сети выбрано `Host-Only` или разные сети. Поставьте `Shared Network` на всех трёх ВМ; проверьте `ip a`, что адреса из `10.211.55.0/24` |
| `ping` не установлен | `sudo apt install -y iputils-ping` |
| Приложение не отвечает на `127.0.0.1:8080` | `sudo journalctl -u skachki -n 50`. Типичная причина — ошибка в `.env` |
| Приложение отвечает локально, но не с других ВМ | Проверьте `APP_HOST=0.0.0.0` в `/opt/horse-racing-devops/.env` и `sudo ss -tlnp \| grep 8080` |
| `ModuleNotFoundError` при старте | Виртуальное окружение не собрано: `sudo -u skachki /opt/horse-racing-devops/.venv/bin/pip install -r /opt/horse-racing-devops/requirements.txt` |
| `curl /api/health` → `"status":"degraded"`, страницы отдают `503` | Служба работает, а СУБД — нет. Это штатное поведение: запустите PostgreSQL (`sudo systemctl start postgresql`) и **обновите страницу** — схема создастся сама, перезапуск `skachki` не нужен |
| PostgreSQL: `connection refused` | `sudo systemctl status postgresql`; проверьте `DATABASE_URL` в `.env` |
| Порт занят | `sudo ss -tlnp \| grep 8080`, затем `sudo bash scripts/install-stand.sh test --port 8081` |
| Не хватает памяти на три ВМ | Уменьшите RAM каждой ВМ до 1.5 ГБ или запускайте по две одновременно |

> **Полезно знать.** Приложение намеренно не падает при недоступной СУБД: стенд
> поднимается, `/api/health` отдаёт `status=degraded`, а страницы — `503` с
> перечнем того, что нужно проверить. Поэтому при защите работы можно показать
> поведение стенда при отказе базы: остановите PostgreSQL и обновите страницу.

## Вопросы для защиты

### Вопрос 1. Типы сетей для виртуальных машин

**Общее.** Все три режима — `virtual network` (в Parallels — *Shared Network*),
`bridge` и `nat` — решают одну задачу: дать виртуальной машине сетевой интерфейс,
не привязывая её напрямую к физическому адаптеру хоста. Во всех случаях гипервизор
создаёт виртуальный коммутатор (vSwitch), к которому подключаются виртуальные
сетевые карты, и обрабатывает кадры Ethernet программно. Внутри ВМ при этом
работает обычный драйвер сетевой карты (в Parallels — `virtio-net`), а адресация
выполняется стандартным стеком TCP/IP гостевой ОС.

**Различия.**

| Режим | Что происходит | Кто выдаёт IP | Видимость ВМ из внешней сети | Типичное применение |
|-------|----------------|---------------|------------------------------|---------------------|
| **Bridged** | Виртуальный адаптер ВМ «встраивается» в физическую сеть хоста как отдельное устройство с собственным MAC | DHCP-сервер физической сети (роутер) | Да, ВМ выглядит как обычный компьютер в сети | ВМ должна быть полноценным участником корпоративной сети |
| **NAT** | Гипервизор подменяет адреса (трансляция адресов и портов); ВМ выходит наружу «через» хост | Встроенный DHCP гипервизора | Нет, извне к ВМ обратиться нельзя без проброса портов | Нужен интернет внутри ВМ, но не нужен входящий доступ |
| **Virtual / Shared Network** | Гипервизор создаёт отдельный виртуальный коммутатор и изолированную подсеть (`10.211.55.0/24` в Parallels) | Встроенный DHCP гипервизора | Нет из внешней сети, но **все ВМ этой сети видят друг друга** | Лабораторные стенды, тестовые кластеры, изоляция от рабочей сети |

В этой работе выбран **Shared Network**: он даёт ровно требуемое заданием 3
поведение «ping от всех ко всем» между тремя ВМ, не выпуская стенды в
университетскую сеть и не требуя проброса портов.

### Вопрос 2. Обработка системных вызовов Unix в виртуальных машинах на хосте Windows

Системный вызов (`syscall`) — это инструкция перехода в режим ядра `syscall`
(x86-64) или `svc` (ARM64). Гостевая программа выполняет этот переход внутри
своего виртуального процессора, и дальше поведение зависит от типа виртуализации.

**Аппаратная виртуализация (VT-x/AMD-V, Hyper-V, KVM).** Гостевая ОС работает в
непривилегированном режиме VMX non-root. Инструкция `syscall` переводит
виртуальный процессор в кольцо 0 **гостевой** ОС — на этом этапе гипервизор не
вмешивается вообще. То есть системный вызов Unix обрабатывается ядром самой
гостевой ОС, и никакой трансляции «Unix→Windows» не происходит. Гипервизор
перехватывает только привилегированные операции, которые затрагивают общие
ресурсы (ввод-вывод, управление памятью, прерывания): попытка такой операции
вызывает `VM exit`, и гипервизор эмулирует её. Набор системных вызовов при этом
целиком определяется гостевой ОС, а не хостом. Именно так работают VirtualBox,
VMware и Hyper-V: ядро Linux в ВМ — настоящее ядро Linux, обслуживающее свои
`syscalls` на своём виртуальном CPU. Различия между семействами вызовов (Unix и
Windows NT) проявляются только в том, что разные гостевые ОС по-разному
используют общий аппаратный интерфейс.

**Виртуализация на уровне ОС (WSL1, контейнеры).** Здесь собственного ядра у
гостя нет, поэтому вызовы действительно нужно транслировать. В WSL1 драйвер `lxcore.sys`
в ядре Windows NT перехватывает системные вызовы Linux и реализует их поверх
нативных API Windows (`NTOSKRNL`/`Win32`); например, `fork()` эмулируется через
механизмы Windows, а обращения к `/proc` и `/sys` строятся динамически. Эта
трансляция неполна по определению, поэтому часть системных вызовов Linux
не поддерживается и производительность ввода-вывода ниже.

**WSL2, Docker Desktop, Hyper-V-контейнеры.** Это уже полноценная аппаратная
виртуализация: Linux-ядро работает в лёгкой ВМ, и системные вызовы Unix
обрабатывает оно само. Docker Desktop на Windows использует WSL2 или
виртуальную машину `MobyLinuxVM`; контейнеры внутри разделяют это ядро.

**Итог.** При «развёртывании ОС Windows» системные вызовы Unix обрабатываются
тремя способами: (1) ядром гостевой ОС в режиме аппаратной виртуализации — самый
распространённый случай; (2) трансляцией вызовов в API Windows (WSL1);
(3) ядром вспомогательной виртуальной машины (WSL2, Docker Desktop). Именно
первый вариант используется в данной работе: Ubuntu в Parallels — это настоящая
гостевая ОС со своим ядром.

### Вопрос 3. Как размещаются виртуальные жёсткие диски, если файловые системы различны

Виртуальный диск гостевой ОС — это **обычный файл на диске хоста**, в котором
последовательно записаны секторы так, как их «видит» гостевая ОС. Поскольку
запись идёт по секторам, файловая система хоста значения не имеет: HFS+/APFS на
macOS, NTFS на Windows и ext4 на Linux одинаково подходят для хранения образа.
Файловая система хоста отвечает только за размещение самого файла образа, а не
за структуру данных внутри него.

**Настройки ВМ и её конфигурация** хранятся в файлах описания: в Parallels —
каталог `*.pvm` с `config.pvs` (XML), в VMware — каталог `*.vmwarevm` с `.vmx`,
в VirtualBox — `*.vbox` (XML). В них записаны объём диска, тип контроллера
(IDE/SATA/NVMe/virtio), количество памяти, параметры сети. Виртуальный BIOS/UEFI
предоставляет гостевой ОС контроллер и диск с заданной геометрией, поэтому
гостевая ОС размечает его так, как считает нужным: GPT, разделы, `ext4`, `xfs`,
`btrfs` — гипервизор в структуру разделов не вмешивается.

**Форматы образов и их свойства.**

| Формат | Особенности |
|--------|-------------|
| RAW / `img` | Побитовая копия диска, максимальная производительность, занимает весь заявленный объём |
| VMDK (VMware, Parallels), VHDX (Hyper-V), VDI (VirtualBox), QCOW2 (QEMU/KVM) | Динамическое выделение: файл растёт по мере записи; снимки состояния, сжатие, шифрование |
| QCow2 / VHDX | Поддержка «разреженных» блоков и `TRIM`-оптимизации |

Есть важный нюанс: если файловые системы гостя и хоста различны, **гипервизор не
выполняет преобразование файловой системы**. Обмен файлами между хостом и гостем
решается отдельным механизмом — общей папкой (`Shared Folders` в Parallels,
`Shared Folders`/`HGFS` в VMware, `vboxsf` в VirtualBox), которая монтируется в
гостя через собственный драйвер, либо сетевыми средствами (SSH, SMB, NFS). В
данной работе обмен выполняется именно так: файлы проекта попадают на стенд по
`git clone` через сеть, а не через общий диск, что дополнительно проверяет
сетевую связность из задания 3.

**Итог.** Виртуальный диск — это файл на хосте (в Parallels+macOS — на
APFS/HFS+), содержащий секторы гостевого диска вместе с его разметкой и
файловой системой; настройки ВМ лежат рядом в XML-описании `config.pvs`. Различие
файловых систем хоста и гостя не создаёт конфликта, потому что гипервизор
оперирует секторами и не разбирает внутреннюю структуру гостевой ФС.
